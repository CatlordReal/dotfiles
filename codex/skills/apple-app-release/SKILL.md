# Apple app release

Confirm the requested release destination and authorization; do not publish to the App Store merely because TestFlight was requested. Consult current official Apple documentation and installed Xcode tool help for requirements that may change. If a relevant local-only project reference exists, consult it and verify its dated facts before use.

1. Before a costly build or upload, verify the installed Xcode and SDK are accepted for the requested distribution using current Apple requirements. Inspect source, repository state, build configuration, custom icon, licenses, privacy disclosures, entitlements, and requested release scope. Resolve real blockers without inventing legal, contact, trader, or export answers. Increment version/build appropriately and freeze the exact source used.
2. Identify the correct paid team, bundle ID, App Store Connect record, certificate and matching private key, and distribution profile. Team membership and App Store Connect roles are distinct. Preserve existing credentials and certificates; avoid revocation or replacement without authorization. Reuse existing Xcode authentication before proposing an API key. Never disclose or commit secrets.
3. Build and archive with the distribution team and matching entitlements. Inspect the archive and exported artifact: signing identity, team, bundle ID, embedded provisioning profile, entitlements, build number, and embedded custom icon. An archive signed for another team may require rebuilding; do not assume export can change its team.
4. Create or update the App Store Connect app record as authorized, then upload the verified build. Track upload acceptance, processing, TestFlight availability, beta review, public link, and device installation separately. For external testing, confirm the build is eligible for external testing rather than internal-only, establish an internal group first, and check current Apple requirements for beta review. Treat first beta review and public-link enablement as separate steps. TestFlight-only distribution does not itself require an unrelated EU App Store trader declaration. Report only observed states.
5. Test relevant app behavior on available platforms and distinguish build, upload, processing, review, device, and physical-use evidence. Do not claim restricted entitlement behavior until Apple approval and matching profile are verified.

For Apple Developer sign-in, Safari saved passwords may be used through native AutoFill. Select the intended account by its visible credential label; inspect accessibility information or a screenshot when needed. Native chooser keyboard selection is acceptable, but do not rely on a fixed number of arrow-key presses. Let the user complete 2FA. Never read or extract passwords or one-time codes, and do not assume every account is signed in. A keychain authorization prompt requires the user to enter the Mac password in the system prompt, not chat. Do not choose Always Allow or weaken keychain partitions without explicit authorization. Verify an actual prompt before requesting action; do not infer one from a slow command.
