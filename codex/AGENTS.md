# Global working style

At task start, read the on-disk global `${CODEX_HOME:-$HOME/.codex}/AGENTS.md` and applicable workspace instructions, then read `$HOME/.agents/skills/caveman/SKILL.md` and `${CODEX_HOME:-$HOME/.codex}/skills/cave-orchestrator/SKILL.md`. Apply both without waiting for a user reminder. A skill catalog, summary, or successful file-existence check does not count as reading its instructions. Re-read after compaction, handoff, or instruction changes.

Always use installed `$caveman`; default user-visible communication Ultra. Preserve exact code, commands, paths, identifiers, diagnostics, errors, safety/consent clarity.

Enforce Ultra on every user-visible reply, including progress updates: use one short sentence when enough; omit repeated plans and tool narration. Before sending, check the active caveman rules and shorten unnecessary prose. Read the installed caveman and cave-orchestrator SKILL.md files at task start; naming a skill is not a substitute for following it. Use longer explanations only when required for correctness, consent, or an explicit request.

Keep active skill contracts in force throughout work. After context compaction, agent handoff, or suspected instruction drift, re-read each active named skill's `SKILL.md` before continuing; do not inject every skill body into every turn.

For every task, use installed `$cave-orchestrator`. It decides orchestration value; default toward orchestration for non-trivial work with safely separable investigation, implementation, testing, or review. Work directly only for simple, short, tightly coupled, sequential tasks. Prefer bounded delegation to `gpt-6.1-terra` at low or medium reasoning when available; choose the lowest-power adequate model. Escalate only for demonstrated inadequacy or concrete risk, and explain why. Never select `gpt-6-astra` unless the user explicitly requests it. After dispatching independent work, wait rather than duplicate it; integrate results as parent. Respect higher-priority delegation restrictions.

Before potentially slow scans, prefer installed fast tools (`rg`, `rg --files`, `fd`, `fzf`) over `grep`/`find`. If a materially useful fast alternative is missing, consider installing it with Homebrew; do not install tools for trivial searches.

Periodically use `$caveman-compress` on eligible agent/memory prose files not recently compressed. Avoid repeated rewrites; follow file-type, backup, exact-preservation, validation rules.

Use Codex Inbox for task notifications under its installed skill. Do not send ntfy notifications unless the user explicitly requests ntfy for the current task; do not automatically fall back to ntfy. Keep notices brief, identify the actual result or needed response, and exclude secrets. Announce success only for completion of the entire user-requested task.

For every confirmed permission or approval request, send the Inbox notification immediately when the request becomes visible, before waiting or starting other work. Include the specific action needing approval so the user can find it. A commentary update does not replace this notification. If a tool call remains pending and the host provides no authoritative approval-state API, say that approval state cannot be observed; do not claim a notification was sent for an unconfirmed request. After an interruption or handoff, check for any confirmed pending request and notify once if it has not already been reported.

All agents must read applicable AGENTS.md instructions and use the installed caveman and cave-orchestrator skills. The parent must include these requirements in delegated work and propagate instruction changes to active agents. Subagents report completed deliverables and questions to the parent; the parent sends the corresponding user-facing Inbox notice once, avoiding duplicate crew notifications. Independently user-facing tasks send their own notifications.

For tool approval notifications, require fresh authoritative evidence that the actual request is awaiting the user; never invent a pending request from a slow call or generic waiting status. If the host lacks live approval-state APIs, state that limitation rather than claiming an automatic watchdog is armed. Questions explicitly issued by the agent and completed deliverables do not require an approval-state adapter. Never approve automatically or bypass checks. If a confirmed approval remains pending after five minutes, use a supported scoped cancellation API when available, save the blocked step, and continue independent work; otherwise leave it pending without repeated alerts.

When work may require app interaction or screenshots, use a task-owned `caffeinate -di` process for GUI testing. `-i` alone does not prevent display sleep and is insufficient for GUI testing. At task start, verify that the display is already on, then immediately start `caffeinate -di` and verify that `PreventUserIdleDisplaySleep` is active before GUI testing. If the display is off or its state is unknown, use `caffeinate -i` only as temporary system-sleep protection while independently verifying graphical access; do not begin GUI testing with only `-i`. Once the display is confirmed on, immediately replace or augment temporary protection with `caffeinate -di`. `-d` prevents idle display sleep; it does not wake an off display or grant graphical permissions. Do not dim, black out, turn off, or lock displays for power saving unless the user explicitly asks for that in the current task. Before every final response ending a turn, stop all `caffeinate` processes started by that task and verify they have exited, even when the overall job is unfinished, blocked, or waiting for the user. Also stop them on cancellation or interruption when cleanup is possible. Restart a task-owned process only when a later active turn needs it. Never stop another task's or the user's keep-awake process. Restore any display settings changed by the task unless the user asked to retain them. Never use broad `pkill` for cleanup.

Every app created or delivered must have an appropriate custom app or launcher icon, including small utilities and Flipper .fap applications. Wire the icon into the platform app metadata, include its source asset in distribution bundles, and verify it is embedded in the final artifact. Do not ship a generic or default icon unless the user explicitly requests it.

Only add theme systems where they serve the product and its users, or when explicitly requested. Do not add theme pickers, large palette collections, or automatic theme scheduling to single-purpose game players (such as Celeste Classic), small utilities, or other interfaces where themes add no practical value. Preserve the game's original visual identity. For apps or websites where a theme system does make sense, provide Catppuccin 4 themes (Latte, Frappé, Macchiato, Mocha), plus Light, Dark, and System choices. Do not add Solar/Sand themes. Support manual overrides and appropriate automatic switching following DuskNotes' semantic theme model. Keep changes smooth, reduced-motion aware, native, readable, and accessible; do not add location access or scheduling solely to satisfy this preference.

When a late user follow-up arrives during active work, capture it in the current task's todo queue with its accepted constraints. Finish the current coherent step, then process that queue; do not drop it or claim it completed early. A new incompatible instruction or user cancellation overrides the current objective. Never create scheduled automation merely because a todo is queued.

When finishing work that changes a visible UI, send representative screenshots of the actual running result. Where animation, gestures, transitions, or other moving behavior matter, also capture and send short GIFs when supported; otherwise provide a short video or clearly explain the capture limitation. Include useful wide and compact views for responsive interfaces. Inspect the captures before sending, keep unrelated or private content out, and distinguish actual captures from mockups. Provide the images inline when possible and link the saved files or gallery. Do not mark requested visual evidence complete before it exists.

Use brief, functional UI copy in every app and website. Avoid marketing slogans, decorative taglines, long explanatory blocks, and clever wording that obscures a control or screen's purpose. Prefer direct labels users can understand immediately. A small amount of personality is fine when it stays concise and clear. Keep necessary safety and permission explanations specific and short.

Never invent wall-clock completion estimates or present intuition as an ETA. Give time estimates only when grounded in observed logs, measured command runtimes, or demonstrated comparable runs; state the evidence, assumptions, and uncertainty. If that evidence is unavailable, report the remaining commands or steps, their difficulty, dependencies, and blockers instead of guessing minutes or hours. Distinguish completed checks from pending work, and never turn an unresolved investigation into a guessed deadline.

When the user asks you to research a problem, asks whether you can do something, or otherwise requests action, carry out the authorized work and follow the findings through to concrete next steps. Do not stop at saying you can, describing a plan, or returning research when you can safely act on it within scope. If an assumed dependency on user-supplied hardware, access, or information turns out not to be needed for the next steps, continue those steps immediately without asking the user to return or reauthorize existing scope. Stop only for a real unresolved dependency, an explicit stop request, or a consequential action requiring new authorization.

For Flipper Zero app work, read and apply `${CODEX_HOME:-$HOME/.codex}/skills/flipper-apps/SKILL.md`; keep project-specific requirements in its scoped reference.


## Task inactivity and approval watchdog

At every task start, launch the task-scoped Codex watchdog for the exact thread ID with a 300-second idle timeout and poll interval no longer than 10 seconds; stop that task-owned watcher before every final response, cancellation, interruption, or handoff. Alert once per idle episode and reset only after fresh rollout activity or verified suppression; when verified suppression ends, start a new full idle window. Generic pending tools, completion-only CommandExecution records, and unified-exec session handles never prove a command is running. For foreground commands expected to exceed the idle timeout, use the reviewed `run-command` wrapper when the tool path permits; suppress only while its wrapper-owned lock is held and heartbeat is fresh. Never wrap `caffeinate`, detached jobs, background dev servers, or other persistent helpers. Track subagents only through bounded authoritative SubagentStart/SubagentStop hook markers mapped from a validated rollout transcript path, never by assuming native session ID equals task thread ID. Send an immediate approval notification only from a fresh authoritative PermissionRequest hook event and mark that idle episode notified; never infer approval from inactivity, PreToolUse, slow tools, or speculative preflight. Never include tool_input, command strings, arguments, outputs, credentials, or private content in marker files, logs, or notifications. Never return an allow/deny decision, rewrite tool input, auto-trust hooks, or modify trusted hashes. Attempt each ntfy delivery once; never retry an ambiguous timeout. Keep watcher state in a private user-owned non-symlink directory outside Codex sessions; keep logs outside session files. Do not install a daemon, LaunchAgent, cron job, or scheduled automation unless the user explicitly requests it.

## Watchdog approval-spam repair — 2026-10-24

`PermissionRequest` fires before approval routing/resolution and does not prove that a person must respond, especially under automatic approval review. Keep its watchdog notification adapter silent and removed from `PermissionRequest` hook configuration; retain the other hooks. Do not re-enable direct notifications from that event or mark an idle episode notified. Notify immediately only when authoritative host state confirms a human-facing request. No such live state adapter is currently wired; state that limitation. Preserve the task-scoped 300-second inactivity fallback, verified foreground-command suppression, one alert per idle episode, explicit question/completion notifications, and normal Codex approval checks. Never change hook trust hashes or make approval decisions. This section supersedes the earlier rule treating every PermissionRequest as a visible human prompt.

Green is reserved for completion of the entire user-requested task. Intermediate steps and completed subtasks are progress, never green dots or completion alerts in Inbox or ntfy. Keep the same substantive information in the current ChatGPT/Codex chat. Inbox is a separate compact conversation; do not mirror the normal Codex transcript. Only actual user questions belong in the request box; blockers, progress, and success belong in the Inbox conversation. Never infer a human approval request from a hook or delay. Subagents report to parents to avoid duplicate notifications.

At the start of every main-agent work turn, before investigation or tool work, publish current status using the installed helper even when no user input is needed: `python3 "${CODEX_HOME:-$HOME/.codex}/skills/codex-inbox/scripts/publish.py" status "Working" --preview "Starting work"`. Status updates only the current activity and summaries: it must never create a purple transcript message or notification, even if progress notifications are enabled. Update status when the work changes; do not echo the user's request as a progress notification. Reserve `progress --report` for a meaningful intermediate result worth retaining in the conversation. Routine starts, plans, tool narration, and "fixing xyz" belong in status. Do not mark idle chats active or send artificial keepalives. Before the final successful response for the entire task, publish `success "Task complete" --done` with a concise actual result. Never leave the last working status as the final task state. If work is unfinished, publish a factual blocker or actual required reply instead; never invent success. Missing configuration or delivery failure must not stop authorized work.

Do not send ntfy notifications unless the user explicitly requests ntfy for the current task. Inbox is the normal notification channel; do not use ntfy as an automatic fallback.
